# 向量库迁移记录：chroma 1.5.9 → FAISS（2026-08-16）

> 背景：Week 4 的 RAG 检索后端在构建 50 万+ 向量规模时反复崩溃，最终经排查确认
> 是 chroma 1.5.9 原生层缺陷，用户批准后迁移至 FAISS 本地方案。
> 本文记录完整的排查过程、决策依据与最终实现，供后续维护参考。

---

## 1. 现象

全量构建索引（120 万消息 → 约 126 万片段）时，chroma 表现出**间歇性原生层挂起/崩溃**：

- 分段续跑时进程在启动期静默死亡（无 Python 异常，仅 jieba 初始化日志）
- `col.count()`、`col.get(include=[])`、`col.query()` 在集合达到一定规模后**挂起不返回**
- 崩溃与规模相关：215K / 501K 集合均出现；<10K 的小集合一切正常
- 分段构建（多进程增量写入）比单进程更易触发

## 2. 排查过程

| 尝试 | 手段 | 结果 |
|---|---|---|
| 多进程分段续跑 | `incremental=True` + `col.get(include=[])` 读已有 id 跳过 | 前 3 段正常，第 4 段（501K）读 id 时崩溃 |
| checkpoint 文件续跑 | 按 `messages.id` 记录进度，不再读集合 id | 写索引正常，但第 2 段又在启动期崩溃；且集合仍不可读 |
| HNSW 参数调整 | `M=12`/`construction_ef=120` ↔ 默认 `M=32` | 小集合测试均正常，大集合依旧崩溃——**与参数无关** |
| 环境隔离测试 | 全新临时目录建小集合 → count/query | ✅ 正常（证明 chroma 本体可用） |
| 决定性测试 | 大集合 count（90s 超时） | **挂起**——集合已处于不可读状态 |

## 3. 根因结论

**chroma 1.5.9 的 Rust 原生核心在 50 万向量规模下存在缺陷**：HNSW 索引累积到一定
规模后，读路径（count / get / query）会无限挂起或静默崩溃，且与 HNSW 参数配置无关。
该问题在多进程分段写入场景下被放大。chroma 官方 1.x 线（Rust core）在此规模下
不可靠，属基础设施硬伤，非本项目代码问题。

## 4. 方案评估与决策

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| **FAISS（faiss-cpu）** | 纯 C++ 成熟稳定；120 万×512 维仅 ~2.4GB 内存；支持跨进程分段续跑 | 需自管元数据存储 | ✅ **采纳**（用户批准） |
| Pinecone 云服务 | 托管免运维 | 有订阅成本、数据出域 | 留作未来外部化备选 |
| 继续调 chroma | — | 根因是版本缺陷，参数无法绕开 | ❌ 放弃 |

## 5. FAISS 实施方案

### 5.1 存储布局（`data/` 下）

| 文件 | 作用 |
|---|---|
| `faiss_index.bin` | FAISS `IndexFlatIP`（512 维），`faiss.write_index` 持久化 |
| `faiss_meta.jsonl` | 边车元数据，**行号 = FAISS id**；每行一个片段：`doc_id / seg / msg_id / talker / time_utc / year_month / start_idx` |
| `index_checkpoint.txt` | 断点续跑：已处理的 `messages.id` |

### 5.2 关键设计

- **向量空间**：embedder 输出 512 维 TF-IDF 且 L2 归一化 → **内积 = 余弦相似度**，
  FAISS 返回的 score 转距离语义（`distance = 1 - score`，越小越相关），与旧接口兼容。
- **接口不变**：`build_index(db_path, progress_cb, incremental, checkpoint)` /
  `search(query, top_k, db_path)` 签名与语义完全保持，`/api/index`、`/api/rag/search`、
  `tools/build_index_runner.py` 均无需改动。
- **checkpoint 续跑**：按消息 id 跳过已处理消息（不读集合已有 id——这正是 chroma
  崩溃点）；分段跨进程安全（`read_index` → `add` → `write_index`）。
- **search 进程内缓存**：索引 + 元数据按文件 mtime 缓存，重建后自动重载；uvicorn
  常驻进程只冷加载一次。
- **兼容存根**：`get_collection()` 保留（`/api/debug/embed` 仍引用），恒返回 `None`，
  调用方走"集合不存在"分支，不影响主功能。

### 5.3 顺带修复的既有 bug（embedder.py）

`TfidfEmbedder.fit` 在**词表不满 512 槽位**时（小语料），单字编号硬编码从
`nb + i`（384+）开始，造成编号空洞 → `self.idf[j]` 越界崩溃。大语料词表恰好
填满 512 槽位故从未触发，本次小库全链路测试暴露。修复：单字从**实际已用槽位**
继续编号（`next_i = len(self.vocab)`）。

## 6. 验证数据（真实数据，120 万消息）

### 6.1 构建性能

| 指标 | 结果 |
|---|---|
| 全量片段数 | 1,267,642 |
| 构建耗时（单进程 checkpoint 模式） | **~290s 一次跑完**（chroma 时代：分段崩溃，累计失败 10+ 次） |
| 索引文件 | `faiss_index.bin` 2.6GB + `faiss_meta.jsonl` 1.05GB |

### 6.2 检索质量（拟合同词表后）

| 查询 | top1 命中 | 距离 |
|---|---|---|
| 晚安 | `晚安`（wxid_zhang, 2024-07） | 0.0000 |
| 今天天气 | `今天天气好清晰`（2026-04） | 0.0331 |
| 项目方案 | `证明项目方资金在流出往大饼挪呗`（2026-05） | 0.2115 |

### 6.3 检索速度（"能否快速分析"的答案）

| 指标 | 结果 |
|---|---|
| fit 词表（全语料一遍） | ~14s |
| 首次检索（含冷加载 2.6GB 索引 + 1.05GB 元数据） | ~14s |
| **热查询单次** | **166-173ms** |

结论：索引加载后单次检索约 **170ms**，可支撑交互式分析；冷启动（构建/重启后首查）
约 14s，属一次性成本。

## 7. 遗留事项

- `/api/debug/embed` 的 chroma 原生 query 对照段已随 `get_collection` 存根失效
  （返回"集合不存在"提示），后续可改写为 FAISS 版对照或移除。
- checkpoint 续跑时 `fit` 全量重算 IDF：新消息极少量时对已嵌入向量影响可忽略；
  若未来出现"增量后检索质量下降"，需引入词表/IDF 持久化或全量重建。
- 数据量再增（>500 万片段）时，可评估 `IndexIVFFlat`（倒排）或降维以控制内存
  （当前 120 万片段内存占用约 3.6GB）。
